# mmf

mmf (working name) is an open file format for machine learning models. It
aims to compete with ONNX and GGUF: smaller to implement, faster to load, and
able to hold any model, from a CNN to an LLM, for inference and for training.

> **Status: spec v0.1 draft, with a Go reference reader and writer.** The
> design rationale is in [docs/design-notes.md](docs/design-notes.md) and
> [docs/adr](docs/adr); the normative text is in [spec](spec).

## In one paragraph

A model file is a binary container: a 64-byte preamble, a binary index, a
graph written in 33 primitive operations, typed metadata, and the weights in
a page-aligned, memory-mappable region. A standard library defines hundreds of
common operations (GELU, softmax, layer norm, attention) as compositions of
the primitives, each with a name and version so a runtime with a faster
kernel can use it. A runtime that implements the 33 primitives runs every
model. Block-quantized dtypes are specified byte for byte, and the file is
treated as untrusted input throughout.

## Using the Go package

```go
f, err := mmf.Open("model.mmf")   // mmap, validate, no copies
defer f.Close()
t, _ := f.Tensor("layers.0.attn.q.weight")
data := f.TensorData(t)           // a slice into the mapping
g, err := f.Graph()               // decoded, validated graph
```

Writing:

```go
w := mmf.NewWriter()
w.AddTensor("w", mmf.F32, []uint64{2, 3}, bytes)
w.AddSection(mmf.SectionGraph, true, graphBytes)
w.WriteFile("model.mmf")          // temp file, fsync, rename
```

Run `go test ./...` for the test suite, including a hostile-file corpus,
fuzz targets for the container, metadata and graph parsers, and the
primitive conformance corpus run against the reference kernels.

## Conformance

The corpus in `testdata/conformance/primitives` holds 1,330 cases covering
all 33 primitives. Expected results come from an independent oracle that
evaluates the spec's definitions exactly (rational arithmetic, or mpmath at
256 bits) and rounds once to the output dtype, so the spec rather than the
Go code is the source of truth. A runtime in any language can load the JSON
files and check itself; see [spec/conformance.md](spec/conformance.md). From
Go:

```go
cases, _ := conformance.LoadDir("testdata/conformance/primitives")
report := conformance.Run(cases, ref.Eval, conformance.IEEE)
```

## A second runtime

`python/` holds a reader and executor in Python and NumPy, written from the
spec with no code shared with the Go implementation. It passes the whole
primitive conformance corpus, rejects the hostile files of
spec/container.md with the same error codes, reads every file of the
compatibility corpus in `testdata/compat`, and runs the tiny Llama from its
mmf file with logits within 6e-7 (relative to the largest logit) of the Go
executor's. It also runs the CNN that `mmf-import` converts from ONNX
(below) and matches onnxruntime's outputs. See
[python/README.md](python/README.md).

## Importing GGUF and safetensors

```
go run ./cmd/mmf-import -bench model.gguf                 # writes model.mmf
go run ./cmd/mmf-import -o model.mmf shard-1.safetensors shard-2.safetensors
```

Tensors are copied without re-quantization: every GGUF block type mmf
defines (Q4_0, Q8_0, Q4_K, Q6_K, MXFP4) has the same layout in both formats,
so a quantized tensor decodes to the same bits. GGUF types mmf does not yet
define (Q5_K, the IQ types, and others) are rejected by name. Metadata keys
keep their names and types. Neither source format carries a usable graph, so
by default the output holds weights and metadata only. `-bench` reports the
size of each file and the time to open it and read every tensor byte;
`cmd/mmf-bench` measures the same for any mix of mmf, GGUF and safetensors
files. Results for a TinyLlama-sized model are in
[docs/benchmarks.md](docs/benchmarks.md).

## Importing ONNX

```
go run ./cmd/mmf-import model.onnx                        # writes model.mmf, with its graph
```

A float32 ONNX model built from the operators of a convolutional network
converts with its graph, so the output runs as it is: Conv (with groups,
strides, dilations and any padding, including `auto_pad`),
BatchNormalization, Relu, Clip, Sigmoid, Tanh, MaxPool, AveragePool,
GlobalAveragePool, Add, Sub, Mul, Div, Gemm, MatMul, Flatten, Reshape,
Transpose, Concat, Softmax, Identity, Dropout and Constant, from opset 7 to
22. Convolutions become `conv2d.v1` and fully connected layers `linear.v1`;
inference-mode BatchNormalization is folded into a per-channel scale and
shift; pooling is written in primitives. Initializers are stored byte for
byte, and a dimension an input names, such as the batch size, stays
symbolic. Any other operator, data type or attribute is rejected by name.
The protobuf is decoded by the importer itself, which keeps the module
free of dependencies.

The tests convert `testdata/onnx/tiny-cnn.onnx`, a small classifier that
uses every supported operator, and compare both runtimes with onnxruntime
on two batch sizes: the outputs agree within 1e-5.

## Exporting from PyTorch

```python
import torch
from torch.export import Dim
from mmf.pytorch import export

model.eval()
export(model, (ids,), "model.mmf",
       dynamic_shapes={"ids": {0: Dim("batch", max=8), 1: Dim("seq", max=2048)}})
```

`mmf.pytorch` (in `python/`, needs PyTorch 2.6 or later) traces the model
with `torch.export` and writes each ATen operator as primitives or a
standard-library call: `linear.v1`, `matmul.v1`, `conv2d.v1` (1-D
convolutions too), `layer_norm.v1`, `rms_norm.v1`, `softmax.v1`,
`attention.v1` for `scaled_dot_product_attention` (causal, masked and
grouped-query), `embedding.v1`, the GELU, SiLU, sigmoid and tanh
composites, and reductions, comparisons, indexing, slicing, concatenation
and pooling in primitives. Parameters are stored byte for byte under their
state-dict names; buffers become constants, and work that depends only on
buffers, such as a rotary table, is computed once at export. Eval-mode
batch norm is folded into a scale and shift. A dimension marked dynamic
stays symbolic, bounded by its `max`; `torch.arange` of a symbolic length
becomes the `iota` of the standard library. Anything else is rejected with
the operator's name. `mmf.pytorch.SUPPORTED` lists the operators.

The tests export a CNN, a 1-D convolutional network, a GPT-style decoder
(tied embeddings, causal attention written both with
`scaled_dot_product_attention` and by hand with a masked buffer) and a
Llama-style decoder (RMSNorm, rotary embeddings, grouped-query attention,
SwiGLU). Both the Python runtime and the Go executor run the float32
exports and match PyTorch within 2e-6 of the largest output, for sequence
lengths and batch sizes other than the ones traced. The Llama exported in
bfloat16 and float16 runs in those dtypes and stays as close to the
float32 model as PyTorch's own result.

A decoder with a static key-value cache exports with the cache in the
graph. A buffer the model writes in `forward` becomes a graph variable
(ADR 0003), ZERO_INIT when it starts as zeros, and writes with
`index_copy_` or `cache[:, :, pos] = k` become `scatter`, so a runtime
updates the cache in place. Positions are an input tensor, so one file
runs both the prompt and every decode step. The tests export a Llama-style
decoder with such a cache and run a prompt and single-token steps in one
session of each runtime: the logits match PyTorch's, and the full forward
pass's, within 2e-6.

## Running a language model

`-graph` makes a GGUF file of the llama architecture (Llama, TinyLlama,
Mistral and others in llama.cpp's llama layout) runnable: the importer
writes the forward pass as an mmf graph from the hyperparameters in the
metadata, with the key-value cache as graph variables (ADR 0003).

```
go run ./cmd/mmf-import -graph -ctx 2048 tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf
go run ./cmd/mmf-run -m tinyllama-1.1b-chat-v1.0.Q4_K_M.mmf -p "Once upon a time" -n 64
```

`mmf-run` tokenizes the prompt with the tokenizer stored in the metadata,
runs it through the graph in one step and then generates one token per
step. Greedy decoding is the default; `-temp` samples instead. The weights
stay quantized in the mapped file and are decoded row by row inside the
matrix products. By default the matrix products are `dequant_matmul_a8`,
which lets a runtime round the activations to 8 bits, as llama.cpp does, so
that it can multiply in integers: in blocks of 256 for K-quant weights
(`dequant_matmul_a8.v2`) and of 32 for the others (`v1`); `-a8=false`
writes `dequant_matmul.v1`,
computed to float32 accuracy. `-ctx` sets the cache length. The cache is
a variable that starts as zeros, so it takes no space in the file; a
session allocates it when it starts. The cache holds keys and values in
f16 (2 bytes per element, read by `attention.v2`); `-kv f32` keeps them in
float32 instead.

The tests check the whole path on a tiny Llama quantized to Q4_K_M by
llama.cpp: token ids against llama.cpp's tokenizer, and the logits of a
prompt and an eight-token greedy continuation against an independent
float64 NumPy forward pass, which is itself checked against llama.cpp.

## Running a graph

```go
p, err := interp.Load(f)                 // f from mmf.Open
s := p.NewSession()                      // holds variables, such as a KV cache
out, err := s.Run(map[string]*ref.Tensor{"x": x})
```

`interp` binds symbolic dimensions from the inputs, runs `while`, `if` and
model-local composites, and applies variable updates atomically after each
run. Of the standard library it runs `matmul.v1`, `linear.v1`, `conv2d.v1`,
`dequant_matmul.v1`, `dequant_matmul_a8.v1`, `dequant_matmul_a8.v2`, `softmax.v1`, `rms_norm.v1`,
`layer_norm.v1`, `mean.v1`, `cumsum.v1`, `exp.v1`, `cos.v1`, `erf.v1`,
`tanh.v1`, `sigmoid.v1`, `silu.v1`, `gelu_erf.v1`, `gelu_tanh.v1`,
`swiglu.v1`, `rope.v1`, `attention.v1`, `attention.v2` and `embedding.v1` by evaluating their canonical bodies on the primitive
kernels; other composites are reported as unsupported. With
`p.FastPaths = true` it runs its own float32 kernels for the composites a
transformer spends its time in (the matrix products, normalisation, rope,
attention, SwiGLU and embedding lookup) and for `conv2d.v1`. Each fast path is tested against
its canonical body. The matrix products and attention use AVX2 kernels on
amd64 (`internal/kernels`), decoding Q4_K, Q6_K, Q8_0, F16 and BF16 weights
inside the dot product, with plain Go elsewhere and under the `purego`
build tag. The 8-bit products of `dequant_matmul_a8` also have NEON kernels
on arm64 and, for the prompt, AMX tile kernels on Intel CPUs that have
them. On a 4-core Xeon a 1.1B Q4_K_M model generates about 31 tokens per
second against llama.cpp's 24, and reads the prompt at 113 against 155
(see [docs/benchmarks.md](docs/benchmarks.md)).
