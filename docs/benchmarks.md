# Benchmarks

How mmf compares with GGUF and safetensors on a model of TinyLlama 1.1B's
size: file size, time to open a file and read its weights, and memory. The
numbers below were measured on one machine and are meant to show orders of
magnitude, not to rank formats to the percent.

## The models

The models are **TinyLlama-shaped, with random weights**, generated by
`tools/gen_bench_models.py`: 22 layers, embedding 2048, 32 query heads over
4 key-value heads, FFN 5632, vocabulary 32000. The machine the benchmarks
ran on cannot download from Hugging Face, so the real TinyLlama files were
not used. Loading and the speed of a forward pass do not depend on the
values of the weights, and the shapes, dtypes and metadata are TinyLlama's,
so the sizes and times are those of the real model.

| file | made by |
| --- | --- |
| `tinyllama-rand-f16.gguf` | the script, F16 as `convert_hf_to_gguf.py` writes it |
| `tinyllama-rand-q4km.gguf` | llama.cpp's quantizer, Q4_K_M |
| `tinyllama-rand-bf16.safetensors` | the script, BF16 with Hugging Face tensor names |
| `q4km.mmf` | `mmf-import tinyllama-rand-q4km.gguf` |
| `q4km-graph.mmf` | `mmf-import -graph -ctx 2048 -a8=false tinyllama-rand-q4km.gguf` |
| `q4km-a8.mmf` | `mmf-import -graph -ctx 2048 tinyllama-rand-q4km.gguf` |
| `bf16.mmf` | `mmf-import tinyllama-rand-bf16.safetensors` |

To reproduce:

```
python3 -P tools/gen_bench_models.py /tmp/bench
go run ./cmd/mmf-import -o /tmp/bench/q4km.mmf /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mmf-import -o /tmp/bench/bf16.mmf /tmp/bench/tinyllama-rand-bf16.safetensors
go run ./cmd/mmf-import -graph -ctx 2048 -o /tmp/bench/q4km-a8.mmf /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mmf-import -graph -ctx 2048 -a8=false -o /tmp/bench/q4km-graph.mmf /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mmf-bench /tmp/bench/*.gguf /tmp/bench/*.safetensors /tmp/bench/*.mmf
go run ./cmd/mmf-bench -cold /tmp/bench/*.gguf /tmp/bench/*.safetensors /tmp/bench/*.mmf
go build -o /tmp/mmf-run ./cmd/mmf-run
python3 tools/bench_generate.py --mmf-run /tmp/mmf-run /tmp/bench/tinyllama-rand-q4km.gguf /tmp/bench/q4km-*.mmf
```

Machine: 4-core Intel Xeon at 2.8 GHz (a cloud VM), 15 GiB of memory,
Linux, Go 1.24.

## File size

| `tinyllama-rand-q4km.gguf` | 667,746,528 | |
| `q4km.mmf` | 668,028,928 | +0.04% |
| `q4km-a8.mmf`, with the graph | 668,160,000 | +0.06% |
| `tinyllama-rand-bf16.safetensors` | 2,200,119,832 | |
| `bf16.mmf` | 2,200,129,536 | +0.0004% |
| `tinyllama-rand-f16.gguf` | 2,200,948,864 | |

Tensors are copied byte for byte, so an mmf file is its source plus the
page alignment of each tensor (4 KiB, against GGUF's 32 bytes) and a binary
index. The graph of the Q4_K_M model adds 128 KiB. Its key-value cache, 92
MiB at a context of 2048, starts as zeros and takes no space in the file
(spec/graph.md, ZERO_INIT).

## Opening and reading

`cmd/mmf-bench` measures each file in a fresh process. *open* is the time
to map the file and parse everything a loader needs before it can use a
tensor: for GGUF and safetensors the header, for mmf `mmf.Open`, which
validates the index, plus decoding the metadata section and, when there is
one, loading the graph. *read* is the time to then touch every byte of
every tensor, in file order, one byte per cache line. *heap* is what the Go
code allocated while opening; *anon* and *mapped* are the process's resident
anonymous and file-backed memory after reading.

Warm page cache, median of 9 runs:

| file | format | open | read | heap | anon | mapped |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | gguf | 2.67 ms | 82 ms | 1.5 MiB | 2.6 MiB | 639 MiB |
| `q4km.mmf` | mmf | 1.82 ms | 83 ms | 1.2 MiB | 2.2 MiB | 640 MiB |
| `q4km-a8.mmf` | mmf + graph | 3.50 ms | 84 ms | 1.6 MiB | 2.7 MiB | 640 MiB |
| `tinyllama-rand-f16.gguf` | gguf | 2.95 ms | 286 ms | 1.5 MiB | 2.5 MiB | 2101 MiB |
| `tinyllama-rand-bf16.safetensors` | safetensors | 1.44 ms | 271 ms | 262 KiB | 1.4 MiB | 2101 MiB |
| `bf16.mmf` | mmf | 0.20 ms | 278 ms | 45 KiB | 1.1 MiB | 2101 MiB |

Cold page cache (each run first drops the file from the cache), median of 7
runs:

| file | format | open | read |
| --- | --- | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | gguf | 3.3 ms | 345 ms |
| `q4km.mmf` | mmf | 3.2 ms | 341 ms |
| `tinyllama-rand-f16.gguf` | gguf | 3.5 ms | 2.55 s |
| `tinyllama-rand-bf16.safetensors` | safetensors | 1.4 ms | 2.26 s |
| `bf16.mmf` | mmf | 0.44 ms | 2.06 s |

What this shows:

- **Opening an mmf file costs almost nothing beyond its metadata.** The
  index is binary and fixed-size, so `bf16.mmf`, whose metadata is small,
  opens in 0.2 ms, 7 times faster than the safetensors file (JSON header)
  and 15 times faster than GGUF (whose header must be walked key by key to
  find the tensors). The Q4_K_M files carry a 32,000-entry tokenizer in
  their metadata, and decoding it takes most of the 1.8 ms, against 2.7 ms
  for GGUF's parser. Decoding and validating the graph adds 1.7 ms.
- Timings below a few milliseconds vary by about a millisecond from one
  set of runs to the next on this machine.
- **Reading the weights costs the same in every format.** All three map the
  file and use the tensor bytes where they lie, so reading is bound by
  memory, or by the disk when the cache is cold. The cold-cache differences
  between formats are within the noise of this machine's disk, which
  ranged from 0.6 s to 3 s for a plain sequential read of the same 2 GiB
  file.
- **None of the formats copies the weights.** Resident memory is the mapped
  file plus one to three MiB.

## Generating text

`tools/bench_generate.py` runs a prompt of 21 tokens and generates 64
tokens greedily, in a fresh process per run, with `mmf-run` for mmf files
and with llama.cpp (through llama-cpp-python 0.3) for the GGUF file. Both
use the 4 cores. *load* is the time until the model is ready to run,
*peak RSS* the process's peak resident memory.

| file | runtime | load | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 670 ms | 123 tok/s | 26.5 tok/s | 1210 MiB |
| `q4km-graph.mmf` | mmf-run | 9 ms | 19.1 tok/s | 9.2 tok/s | 911 MiB |
| `q4km-a8.mmf` | mmf-run | 9 ms | 25.6 tok/s | 14.4 tok/s | 931 MiB |

Median of 5 runs.

`q4km-graph.mmf` is imported with `-a8=false`: its matrix products are
`dequant_matmul.v1`, computed to float32 accuracy. `q4km-a8.mmf` is the
default import, whose matrix products are `dequant_matmul_a8.v1`: the
activations may be rounded to 8 bits, as llama.cpp does, which lets the
products run in integer arithmetic. Its logits stay within llama.cpp's own
distance from a float64 forward pass (`cmd/mmf-run`'s `TestGenerateA8`).

Before the kernels in `internal/kernels`, the same model generated 0.88
tokens per second. llama.cpp is still about 1.8 times faster at generation
and 5 times faster on the prompt, where it multiplies matrices by matrices
rather than row by row. mmf-run's load is fast because nothing is read
until the first step.

### After the worker pool and prefetch

Measured on a different machine from the tables above: 4 cores of an
Intel Xeon at 2.1 GHz (a cloud VM with AVX-512, which none of the kernels
use yet), 15 GiB of memory, Linux, Go 1.24, llama-cpp-python 0.3.16 built
on the machine. Same models, same script, median of 3 runs.

| file | runtime | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 132.9 tok/s | 25.0 tok/s | 1297 MiB |
| `q4km-graph.mmf` | mmf-run before | 21.8 tok/s | 11.1 tok/s | 843 MiB |
| `q4km-graph.mmf` | mmf-run after | 27.5 tok/s | 16.5 tok/s | 911 MiB |
| `q4km-a8.mmf` | mmf-run before | 31.3 tok/s | 15.1 tok/s | 932 MiB |
| `q4km-a8.mmf` | mmf-run after | 32.8 tok/s | 26.7 tok/s | 862 MiB |

Two changes made the difference (docs/design-notes.md, "Speed plan after
v0.1", step 1). The executor keeps its worker goroutines between parallel
calls, spinning for 0.2 ms before they sleep, instead of starting new ones
for each of the few hundred calls of a token; that took the CPU use of a
generation step from 2.6 to 3.4 of the 4 cores. And the Q4_K and Q6_K
kernels prefetch the weights two rows ahead, which let each core read them
at nearly twice the rate. Generation is now as fast as llama.cpp's on this
machine. The prompt is still 4 times slower: llama.cpp multiplies the
prompt's activations as a matrix, mmf-run still row by row.
