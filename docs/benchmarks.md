# Benchmarks

How mim compares with GGUF and safetensors on a model of TinyLlama 1.1B's
size: file size, time to open a file and read its weights, and memory. The
numbers below were measured on one machine and are meant to show orders of
magnitude, not to rank formats to the percent.

## The models

The models are **TinyLlama-shaped, with random weights**, generated by
`tools/gen_bench_models.py`: 22 layers, embedding 2048, 32 query heads over
4 key-value heads, FFN 5632, vocabulary 32000. The machine the benchmarks
ran on cannot download from Hugging Face, so the real TinyLlama files were
not used. Loading and the speed of a forward pass do not depend on the
values of the weights, and the shapes, dtypes and metadata are TinyLlama's,
so the sizes and times are those of the real model.

| file | made by |
| --- | --- |
| `tinyllama-rand-f16.gguf` | the script, F16 as `convert_hf_to_gguf.py` writes it |
| `tinyllama-rand-q4km.gguf` | llama.cpp's quantizer, Q4_K_M |
| `tinyllama-rand-bf16.safetensors` | the script, BF16 with Hugging Face tensor names |
| `q4km.mim` | `mim-import tinyllama-rand-q4km.gguf` |
| `q4km-graph.mim` | `mim-import -graph -ctx 2048 -a8=false tinyllama-rand-q4km.gguf` |
| `q4km-a8.mim` | `mim-import -graph -ctx 2048 tinyllama-rand-q4km.gguf` |
| `bf16.mim` | `mim-import tinyllama-rand-bf16.safetensors` |

To reproduce:

```
python3 -P tools/gen_bench_models.py /tmp/bench
go run ./cmd/mim-import -o /tmp/bench/q4km.mim /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mim-import -o /tmp/bench/bf16.mim /tmp/bench/tinyllama-rand-bf16.safetensors
go run ./cmd/mim-import -graph -ctx 2048 -o /tmp/bench/q4km-a8.mim /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mim-import -graph -ctx 2048 -a8=false -o /tmp/bench/q4km-graph.mim /tmp/bench/tinyllama-rand-q4km.gguf
go run ./cmd/mim-bench /tmp/bench/*.gguf /tmp/bench/*.safetensors /tmp/bench/*.mim
go run ./cmd/mim-bench -cold /tmp/bench/*.gguf /tmp/bench/*.safetensors /tmp/bench/*.mim
go build -o /tmp/mim-run ./cmd/mim-run
python3 tools/bench_generate.py --mim-run /tmp/mim-run /tmp/bench/tinyllama-rand-q4km.gguf /tmp/bench/q4km-*.mim
```

Machine: 4-core Intel Xeon at 2.8 GHz (a cloud VM), 15 GiB of memory,
Linux, Go 1.24.

Tensors are copied byte for byte, so a mim file is its source plus the
page alignment of each tensor (4 KiB, against GGUF's 32 bytes) and a binary
index. The graph of the Q4_K_M model adds 128 KiB. Its key-value cache, 92
MiB at a context of 2048, starts as zeros and takes no space in the file
(spec/graph.md, ZERO_INIT).

## Opening and reading

`cmd/mim-bench` measures each file in a fresh process. *open* is the time
to map the file and parse everything a loader needs before it can use a
tensor: for GGUF and safetensors the header, for mim `mim.Open`, which
validates the index, plus decoding the metadata section and, when there is
one, loading the graph. *read* is the time to then touch every byte of
every tensor, in file order, one byte per cache line. *heap* is what the Go
code allocated while opening; *anon* and *mapped* are the process's resident
anonymous and file-backed memory after reading.

Warm page cache, median of 9 runs:

| file | format | open | read | heap | anon | mapped |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | gguf | 2.67 ms | 82 ms | 1.5 MiB | 2.6 MiB | 639 MiB |
| `q4km.mim` | mim | 1.82 ms | 83 ms | 1.2 MiB | 2.2 MiB | 640 MiB |
| `q4km-a8.mim` | mim + graph | 3.50 ms | 84 ms | 1.6 MiB | 2.7 MiB | 640 MiB |
| `tinyllama-rand-f16.gguf` | gguf | 2.95 ms | 286 ms | 1.5 MiB | 2.5 MiB | 2101 MiB |
| `tinyllama-rand-bf16.safetensors` | safetensors | 1.44 ms | 271 ms | 262 KiB | 1.4 MiB | 2101 MiB |
| `bf16.mim` | mim | 0.20 ms | 278 ms | 45 KiB | 1.1 MiB | 2101 MiB |

Cold page cache (each run first drops the file from the cache), median of 7
runs:

| file | format | open | read |
| --- | --- | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | gguf | 3.3 ms | 345 ms |
| `q4km.mim` | mim | 3.2 ms | 341 ms |
| `tinyllama-rand-f16.gguf` | gguf | 3.5 ms | 2.55 s |
| `tinyllama-rand-bf16.safetensors` | safetensors | 1.4 ms | 2.26 s |
| `bf16.mim` | mim | 0.44 ms | 2.06 s |

What this shows:

- **Opening a mim file costs almost nothing beyond its metadata.** The
  index is binary and fixed-size, so `bf16.mim`, whose metadata is small,
  opens in 0.2 ms, 7 times faster than the safetensors file (JSON header)
  and 15 times faster than GGUF (whose header must be walked key by key to
  find the tensors). The Q4_K_M files carry a 32,000-entry tokenizer in
  their metadata, and decoding it takes most of the 1.8 ms, against 2.7 ms
  for GGUF's parser. Decoding and validating the graph adds 1.7 ms.
- Timings below a few milliseconds vary by about a millisecond from one
  set of runs to the next on this machine.
- **Reading the weights costs the same in every format.** All three map the
  file and use the tensor bytes where they lie, so reading is bound by
  memory, or by the disk when the cache is cold. The cold-cache differences
  between formats are within the noise of this machine's disk, which
  ranged from 0.6 s to 3 s for a plain sequential read of the same 2 GiB
  file.
- **None of the formats copies the weights.** Resident memory is the mapped
  file plus one to three MiB.

## Generating text

`tools/bench_generate.py` runs a prompt of 21 tokens and generates 64
tokens greedily, in a fresh process per run, with `mim-run` for mim files
and with llama.cpp (through llama-cpp-python 0.3) for the GGUF file. Both
use the 4 cores. *load* is the time until the model is ready to run,
*peak RSS* the process's peak resident memory.

| file | runtime | load | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 670 ms | 123 tok/s | 26.5 tok/s | 1210 MiB |
| `q4km-graph.mim` | mim-run | 9 ms | 19.1 tok/s | 9.2 tok/s | 911 MiB |
| `q4km-a8.mim` | mim-run | 9 ms | 25.6 tok/s | 14.4 tok/s | 931 MiB |

Median of 5 runs.

`q4km-graph.mim` is imported with `-a8=false`: its matrix products are
`dequant_matmul.v1`, computed to float32 accuracy. `q4km-a8.mim` is the
default import, whose matrix products are `dequant_matmul_a8.v1`: the
activations may be rounded to 8 bits, as llama.cpp does, which lets the
products run in integer arithmetic. Its logits stay within llama.cpp's own
distance from a float64 forward pass (`cmd/mim-run`'s `TestGenerateA8`).

Before the kernels in `internal/kernels`, the same model generated 0.88
tokens per second. llama.cpp is still about 1.8 times faster at generation
and 5 times faster on the prompt, where it multiplies matrices by matrices
rather than row by row. mim-run's load is fast because nothing is read
until the first step.

### After the first speed work

Measured on a different machine from the tables above: 4 cores of an
Intel Xeon at 2.1 GHz (a cloud VM with AVX-512, which none of the kernels
use yet), 15 GiB of memory, Linux, Go 1.24, llama-cpp-python 0.3.16 built
on the machine. Same models, same script, median of 3 runs.

| file | runtime | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 131.1 tok/s | 25.1 tok/s | 1297 MiB |
| `q4km-graph.mim` | mim-run before | 21.8 tok/s | 11.1 tok/s | 843 MiB |
| `q4km-graph.mim` | mim-run after | 27.9 tok/s | 15.7 tok/s | 904 MiB |
| `q4km-a8.mim` | mim-run before | 31.3 tok/s | 15.1 tok/s | 932 MiB |
| `q4km-a8.mim` | mim-run after | 59.2 tok/s | 29.4 tok/s | 920 MiB |

These are steps 1 and 2 of the speed plan in docs/design-notes.md:

- The executor keeps its worker goroutines between parallel calls,
  spinning for 0.2 ms before they sleep, instead of starting new ones for
  each of the few hundred calls of a token. That took the CPU use of a
  generation step from 2.6 to 3.4 of the 4 cores.
- The Q4_K and Q6_K kernels prefetch the weights two rows ahead, which let
  each core read them at nearly twice the rate.
- The 8-bit kernels multiply one row of Q4_K or Q6_K weights by four rows
  of activations at once, decoding the weights once for all four. Each of
  the four results is bit for bit what the one-row kernel returns, so the
  output does not depend on how many tokens are run together.
- Attention stops at the last key the mask allows, instead of walking the
  whole cache, and permutations of heads copy rows instead of computing
  every index.

Generation is now faster than llama.cpp's on this machine. The prompt is
still 2.2 times slower; llama.cpp uses the machine's AVX-512 and VNNI
instructions there, which mim's kernels do not yet (step 3).

### Activation blocks of 256

Same machine and script, median of 3 runs. `q4km-a8k.mim` is the same GGUF
imported again: its K-quant matrix products are now
`dequant_matmul_a8.v2` with blocks of 256, where `q4km-a8.mim` has `v1`
with blocks of 32. Both run with the same mim-run.

| file | runtime | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 145.7 tok/s | 26.4 tok/s | 1296 MiB |
| `q4km-a8.mim` | mim-run, blocks of 32 | 60.1 tok/s | 26.3 tok/s | 901 MiB |
| `q4km-a8k.mim` | mim-run, blocks of 256 | 70.9 tok/s | 31.5 tok/s | 876 MiB |

With one activation scale per weight block, the kernels add up the
integer products of the whole block and convert to float32 once, instead
of once per 32. The four-row kernels got 16% (Q4_K) and 29% (Q6_K) faster
alone, the prompt 18% and generation 20%. The prompt is still 2.1 times
slower than llama.cpp's. The llama-cpp-python build on this machine
reports AMX_INT8, AVX512_VNNI and REPACK, so llama.cpp most likely
multiplies the prompt with AMX tiles on weights repacked at load; that
is a different kind of kernel from the AVX2 ones here, not a matter of
block size. On the tiny test model the largest logit difference from the
float64 oracle went from 0.33 to 0.41, still under llama.cpp's 0.53.

### AMX tiles

Same machine and script, median of 5 runs, with a 21-token prompt. The
Xeon has AMX, which the Linux kernel lets a process use once it asks
(`arch_prctl(ARCH_REQ_XCOMP_PERM)`). Both rows run the same
`q4km-a8k.mim`; "before" is mim-run at the previous step.

| file | runtime | prompt | generation | peak RSS |
| --- | --- | ---: | ---: | ---: |
| `tinyllama-rand-q4km.gguf` | llama.cpp | 154.8 tok/s | 23.8 tok/s | 1314 MiB |
| `q4km-a8k.mim` | mim-run before | 65.9 tok/s | 28.5 tok/s | 920 MiB |
| `q4km-a8k.mim` | mim-run with AMX | 112.8 tok/s | 31.3 tok/s | 1013 MiB |

llama.cpp's prompt speed varied from 152 to 191 tokens per second between
runs. With a 223-token prompt mim-run reached about 120. The matrix
products of 16 or more rows now go to AMX tile kernels, which take 4 to 7
picoseconds per multiply-add on one core against 25 to 30 for the
four-row AVX2 kernels (`go test -bench TileDot ./internal/kernels`).
Quantizing the activations moved to assembly as well, which a profile
showed next. Generation still runs one row at a time and does not use
the tiles.


### Long prompts

Measured on another machine: 4 cores of an Intel Xeon at 2.8 GHz (a cloud
VM with AVX-512 and VNNI but no AMX, so the prompt runs on the four-row
AVX2 kernels), 15 GiB of memory, Linux, Go 1.24, llama-cpp-python 0.3.16
built on the machine. Same `q4km-a8k.mim` and GGUF, median of 5 runs.
The 38-token prompt is `tools/bench_generate.py`'s sentence; the 741-token
one is the same sentence 20 times (`--repeat 20`). "before" is mim-run at
the previous step.

| prompt | runtime | prompt | generation | peak RSS |
| ---: | --- | ---: | ---: | ---: |
| 38 tokens | llama.cpp | 102.9 tok/s | 25.9 tok/s | 1185 MiB |
| 38 tokens | mim-run before | 67.7 tok/s | 30.0 tok/s | 922 MiB |
| 38 tokens | mim-run after | 79.8 tok/s | 31.3 tok/s | 739 MiB |
| 741 tokens | llama.cpp | 122.8 tok/s | 22.5 tok/s | 1248 MiB |
| 741 tokens | mim-run before | 39.4 tok/s | 11.7 tok/s | 4529 MiB |
| 741 tokens | mim-run after | 85.5 tok/s | 25.3 tok/s | 965 MiB |

Before this step mim-run's prompt speed fell by half as the prompt grew,
and its memory grew with it; llama.cpp's does neither. A profile showed
four causes:

- Each weight row of a matrix product read the whole prompt's
  activations, which for a long prompt do not fit in a core's cache. The
  products now take the activations in blocks of 32 KiB, and each piece of
  weight rows runs over one block before the next. Each row's result is
  bit for bit what it was.
- Attention called a dot product, a float64 exponential and an axpy per
  key. Kernels now compute the scores of one query against a run of keys,
  the softmax in float32 (within 2 units in the last place of exp), and
  the weighted sum of the values, which is bit for bit what the axpy loop
  gave. Attention went from 17% of the prompt's time to 5%.
- RMS norm, RoPE and SwiGLU copied their input on one core before
  working on it. They now write their output directly, in parallel.
- The executor kept every value of a run until the run ended: for a
  741-token prompt, 2.4 GB of activations, which also slowed the
  generation that followed. It now drops each value after the last op
  that reads it.

mim-run also converts only the last position's logits to pick the next
token, instead of all of them. The prompt is still 1.3 to 1.4 times slower
than llama.cpp's here; the matrix products are now 80% of its time.

### VNNI kernels

Same machine as 'Long prompts', median of 5 runs. "before" is mim-run at
the previous step; both run the same `q4km-a8k.mim`.

| prompt | runtime | prompt | generation | peak RSS |
| ---: | --- | ---: | ---: | ---: |
| 38 tokens | llama.cpp | 105.2 tok/s | 23.7 tok/s | 1184 MiB |
| 38 tokens | mim-run before | 77.6 tok/s | 29.9 tok/s | 739 MiB |
| 38 tokens | mim-run with VNNI | 87.0 tok/s | 30.3 tok/s | 742 MiB |
| 741 tokens | llama.cpp | 117.2 tok/s | 21.0 tok/s | 1248 MiB |
| 741 tokens | mim-run before | 82.9 tok/s | 25.1 tok/s | 984 MiB |
| 741 tokens | mim-run with VNNI | 117.1 tok/s | 24.7 tok/s | 1014 MiB |

llama.cpp's prompt speed at 741 tokens ranged from 117 to 123 tokens per
second between sets of runs, and mim-run's with VNNI from 117 to 125. On
CPUs with AVX-512 VNNI and without AMX, the Q4_K and Q6_K products of 12 or
more prompt rows now go to kernels that take 16 activation rows at once:
one VPDPBUSD multiplies four weight quants by four quants of each of the
16 rows. On one core of this Xeon (`go test -bench 'TileDot|dot4x256'
./internal/kernels`), with 64 activation rows, they take 13 picoseconds
per multiply-add for Q4_K and 14 for Q6_K, against 25 and 31 for the
four-row AVX2 kernels. The 38-token prompt has only two full groups of
16 rows and is still bound by the serial steps between the products.

### A key-value cache in f16

Same machine, median of 3 runs. Both files come from the same GGUF with
`mim-import -graph -ctx 2048`; one with `-kv f32`, the other with the new
default, `-kv f16`.

| prompt | cache | prompt | generation | peak RSS |
| ---: | --- | ---: | ---: | ---: |
| 38 tokens | f32 | 78.0 tok/s | 31.5 tok/s | 741 MiB |
| 38 tokens | f16 | 86.8 tok/s | 27.1 tok/s | 700 MiB |
| 741 tokens | f32 | 120.1 tok/s | 26.7 tok/s | 1024 MiB |
| 741 tokens | f16 | 119.3 tok/s | 24.0 tok/s | 931 MiB |
| 741 tokens | llama.cpp | 116.4 tok/s | 20.1 tok/s | 1248 MiB |

The cache of TinyLlama at a context of 2048 takes 46 MiB instead of 92,
and the peak drops by 41 MiB at 38 tokens and 93 MiB at 741. The speed
differences are run to run noise on this shared machine: alternating eight
200-token runs gave 27 to 31 tokens per second for either file, and a CPU
profile puts the extra time in the matrix products, which the cache does
not touch. Attention reads half the bytes per token, but at these lengths
it is under 3% of a step; the gain grows with the context.

## 7 to 8B models

Llama 3 8B, Mistral 7B v0.1 and Qwen2.5 7B, made by
`tools/gen_big_models.py` with the shapes, hyperparameters and
tokenizers of the released models and random weights, quantized to
Q4_K_M by llama.cpp. As for TinyLlama, the machine cannot download the
real weights; the tokenizers come from the Python packages that ship
them (llama-models, mistral-common and dashscope). Llama 3 and Qwen use
byte-level BPE tokenizers, which `tokenizer` now reads (`tokenizer.BPE`),
and Qwen the qwen2 architecture, with biases on the query, key and value
projections and rope over the two halves of each head, which
`mim-import -graph` now builds.

```
pip download --no-deps -d /tmp/wheels llama-models mistral-common dashscope
python3 -P tools/gen_big_models.py /tmp/wheels /tmp/big
go run ./cmd/mim-import -graph -ctx 2048 -o /tmp/big/llama3.mim /tmp/big/llama3-rand-q4km.gguf
python3 -I tools/bench_generate.py --tokens 32 --mim-run /tmp/mim-run /tmp/big/llama3-rand-q4km.gguf /tmp/big/llama3.mim
```

Each model was checked against llama.cpp before it was timed: for
prompts of 10 to 20 tokens, the logits of every position correlate with
llama.cpp's at 0.9993 or more, the largest difference is 0.18 for logits
with a standard deviation of 1.0, and the most likely token is the same
at all but one of 48 positions. With random weights the top logits are
often close, so greedy continuations part after a few tokens. The byte-level
BPE tokenizer gives llama.cpp's token ids for all of 424 test strings
with each of the two vocabularies (code, digits, whitespace runs,
contractions, CJK, emoji, invalid UTF-8 aside).

Machine: 4 cores of an Intel Xeon at 2.1 GHz with AMX (a cloud VM), 15
GiB of memory, Linux, Go 1.24, llama-cpp-python 0.3.16 built on the
machine. Median of 3 runs, 32 generated tokens; the short prompt is the
script's sentence (18 or 19 tokens with these vocabularies), the long one
the sentence 10 times (`--repeat 10`, 180 or 181 tokens).

| model | prompt | runtime | load | prompt | generation | peak RSS |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| Mistral 7B | 19 | llama.cpp | 1431 ms | 27.2 tok/s | 4.7 tok/s | 8527 MiB |
| Mistral 7B | 19 | mim-run | 10 ms | 22.0 tok/s | 7.0 tok/s | 4382 MiB |
| Mistral 7B | 181 | llama.cpp | 2018 ms | 36.2 tok/s | 4.9 tok/s | 8568 MiB |
| Mistral 7B | 181 | mim-run | 9 ms | 43.8 tok/s | 6.5 tok/s | 4501 MiB |
| Llama 3 8B | 19 | llama.cpp | 2893 ms | 26.3 tok/s | 4.4 tok/s | 7944 MiB |
| Llama 3 8B | 19 | mim-run | 78 ms | 15.7 tok/s | 6.1 tok/s | 4721 MiB |
| Llama 3 8B | 181 | llama.cpp | 2561 ms | 41.8 tok/s | 4.4 tok/s | 9265 MiB |
| Llama 3 8B | 181 | mim-run | 70 ms | 39.1 tok/s | 6.7 tok/s | 4903 MiB |
| Qwen2.5 7B | 18 | llama.cpp | 2025 ms | 30.1 tok/s | 4.5 tok/s | 8805 MiB |
| Qwen2.5 7B | 18 | mim-run | 69 ms | 21.2 tok/s | 6.8 tok/s | 4356 MiB |
| Qwen2.5 7B | 180 | llama.cpp | 1276 ms | 38.1 tok/s | 4.8 tok/s | 8805 MiB |
| Qwen2.5 7B | 180 | mim-run | 78 ms | 45.7 tok/s | 6.4 tok/s | 4569 MiB |

The runs of the long prompts generated 16 tokens.

- **Generation is 1.3 to 1.5 times faster than llama.cpp's** on all three.
  At this size a step reads 4.4 to 4.9 GB of weights, and both runtimes
  are bound by memory; mim-run reads each weight row once per step from
  the mapped file.
- **mim-run uses half the memory.** llama.cpp's peak is about twice the
  file: it repacks the weights at load into a second copy laid out for its
  AMX and AVX-512 kernels (llama-cpp-python reports `REPACK`). mim-run
  uses the weights where they lie in the mapped file, and starts in
  milliseconds where llama.cpp takes one to three seconds.
- **Short prompts are 1.2 to 1.7 times slower**, long ones as fast or
  faster. A profile puts 70% of a 19-token prompt in the AMX kernels,
  which decode each block of 16 weight rows to bytes for only two groups
  of activation rows; llama.cpp lays its weights out once, at load, at the
  cost of the second copy. Llama 3 and Qwen also compute logits for every
  prompt position over vocabularies of 128,256 and 152,064 tokens, where
  llama.cpp computes only the last one's: 7% of the prompt's
  multiply-adds.

## Faster prompts on AMX

Same machine as the 7 to 8B models, median of 5 runs for TinyLlama (64
generated tokens) and of 3 for the large models (32). "main" is mim-run
before this step. The machine is a shared cloud VM, and repeated runs of
the same command vary by up to 15%.

| model | prompt | llama.cpp | mim-run main | mim-run now |
| --- | ---: | ---: | ---: | ---: |
| TinyLlama 1.1B | 38 | 157.6 tok/s | 126.2 tok/s | 179.2 tok/s |
| TinyLlama 1.1B | 741 | 200.9 tok/s | 181.4 tok/s | 213.1 tok/s |
| Mistral 7B | 19 | 27.5 tok/s | 22.0 tok/s | 23.9 tok/s |
| Mistral 7B | 181 | 36.2 tok/s | 43.8 tok/s | 60.6 tok/s |
| Llama 3 8B | 19 | 25.5 tok/s | 15.7 tok/s | 18.1 tok/s |
| Llama 3 8B | 181 | 41.8 tok/s | 39.1 tok/s | 55.5 tok/s |
| Qwen2.5 7B | 18 | 28.0 tok/s | 21.2 tok/s | 21.3 tok/s |
| Qwen2.5 7B | 180 | 38.1 tok/s | 45.7 tok/s | 56.0 tok/s |

Generation and peak memory are unchanged (TinyLlama 36.9 tok/s and 695
MiB; the large models 6.6 to 7.1 tok/s and 4.4 to 4.9 GiB). The
large-model "main" column and llama.cpp's long-prompt figures are those of
the previous section.

mim-run now reads TinyLlama's prompts faster than llama.cpp, short or
long, and the large models' long prompts 1.3 to 1.7 times faster. What
changed:

- **Activation layout.** The rows of activations are laid out for the
  tile products by group of 16 rows, one goroutine per group, so that no
  two goroutines write the same cache line, and the Q6_K sums of 16 that
  only the VNNI kernels read are no longer computed on AMX.
- **Buffers are reused.** The quantized activations, their tile layout
  and the kernels' scratch space come from pools instead of being
  allocated for each matrix product.
- **The weights are prefetched** two blocks ahead in the AMX kernels'
  decoding loops.
- **The results are written one weight row at a time**, straight from
  the kernel's totals, instead of through a second pass.
- **SwiGLU is vectorized** (`kernels.SiluMulF32`, AVX2), within
  `swiglu.v1`'s tolerance down to the smallest normal float: it computes
  exp(-|x|/2) and squares it, so the result does not round to zero where
  silu(x) is still a normal float. It took 11% of a long prompt.

Short prompts of the large models are still 10 to 30% slower than
llama.cpp's. They are measured in a fresh process, which maps the 4.4 to
4.9 GB file and faults its pages in during the first prompt, where
llama.cpp reads and repacks the file during its 1 to 3 second load; in a
process that has already run a prompt, Mistral's 19 tokens take 0.64 s
(29.5 tok/s). The rest is the cost of decoding each block of 16 weight
rows for a single group of activations, which llama.cpp avoids with its
repacked copy of the weights.

## arm64

The `bench-arm` workflow (`.github/workflows/bench-arm.yml`) runs on
GitHub's macOS runner: an Apple M1 (virtual), 3 cores, Go 1.24, and
llama-cpp-python 0.3.16 built for the CPU only (Metal and BLAS off). Its
first run was on the random-weight TinyLlama: median of 5 runs at 38 prompt
tokens and of 3 runs at 741, with 64 generated tokens each.

| prompt | runtime | load | prompt | generation | peak RSS |
| ---: | --- | ---: | ---: | ---: | ---: |
| 38 | llama.cpp | 2603 ms | 59.1 tok/s | 47.8 tok/s | 762 MiB |
| 38 | mim-run | 6 ms | 60.3 tok/s | 27.6 tok/s | 670 MiB |
| 741 | llama.cpp | 2823 ms | 60.6 tok/s | 34.6 tok/s | 817 MiB |
| 741 | mim-run | 11 ms | 15.7 tok/s | 6.5 tok/s | 913 MiB |

That first run had NEON kernels only for the 8-bit matrix products.
Attention (scores, softmax, the weighted sum of values, and the f16 cache
decoded one element at a time) and SwiGLU ran in plain Go, and attention's
cost grows with the context, which is why the 741-token prompt and the
generation after it were four to five times slower than llama.cpp's.

With NEON kernels for attention, SwiGLU and the float32 dot products
(`internal/kernels/vec_arm64.s`), a later run gave the table below. That
runner was faster than the first one, llama.cpp included, so compare the
rows of one table, not across tables.

| prompt | runtime | load | prompt | generation | peak RSS |
| ---: | --- | ---: | ---: | ---: | ---: |
| 38 | llama.cpp | 1874 ms | 95.5 tok/s | 63.0 tok/s | 763 MiB |
| 38 | mim-run | 4 ms | 123.4 tok/s | 57.7 tok/s | 679 MiB |
| 741 | llama.cpp | 1581 ms | 88.2 tok/s | 60.3 tok/s | 817 MiB |
| 741 | mim-run | 3 ms | 115.6 tok/s | 53.3 tok/s | 927 MiB |

Prompts now read about 30% faster than llama.cpp's at both lengths, and
generation is 8 to 12% slower instead of 40 to 80%. The CPU profile of
the 741-token run (printed by the workflow) puts 61% of the time in the
8-bit matrix product kernels and 10% in attention.

## Real weights

The released models, as published in Q4_K_M by bartowski on Hugging Face,
checked against the SHA-256 the site lists:
`Meta-Llama-3-8B-Instruct-Q4_K_M.gguf`,
`Mistral-7B-Instruct-v0.3-Q4_K_M.gguf` (v0.3, with a 32,768-token
vocabulary, where the random-weight Mistral above is v0.1) and
`Qwen2.5-7B-Instruct-Q4_K_M.gguf`. Each was imported with
`mmf-import -graph -ctx 4096` and ran as it was: no fixes to the
importer, the tokenizers or the executor were needed.

```
$ mmf-run -m llama3.mmf -p "The capital of France is" -n 32
The capital of France is Paris, which is located in the north-central part of the country. Paris is the most populous city in France and is known for its stunning architecture, art museums
```

### Output against llama.cpp

Four prompts (a fact, the start of a Python function, a story, a
multiplication), up to 48 greedy tokens each, with mmf-run's default
`dequant_matmul_a8` file and with llama.cpp on the GGUF file:

| model | same token ids | same top token over the prompt | identical continuations |
| --- | :---: | ---: | :---: |
| Llama 3 8B | 4 of 4 | 56 of 57 positions | 2 of 4 |
| Mistral 7B v0.3 | 4 of 4 | 67 of 69 | 3 of 4 |
| Qwen2.5 7B | 4 of 4 | 53 of 55 | 1 of 4 |

The tokenizers give llama.cpp's ids for every prompt. Where two
continuations part, they part at a near-tie. For Mistral and Qwen the
logits at each of those positions were compared in three runtimes:
llama.cpp, mmf-run's default file, and the same model imported with
`-a8=false`, whose matrix products keep the activations in float32 and
stand in for the exact result. The top two logits are within 0.25 of
each other in all three, and llama.cpp and mmf-run are about as far from
the float32 file as each other (largest logit differences of 0.3 to 0.4 for Mistral, 0.7 to 2.1 for
Qwen, whose logits span about 40). At Mistral's Python prompt, for
example, llama.cpp's logits for `   ` and ` if` are both 16.08, and
mmf-run picks `   `, as the float32 file does. Every continuation reads
as fluent text, and both runtimes answer 391 to 17 × 23.
